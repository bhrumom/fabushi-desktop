## 279-290: emoji resources

Orders 279-286 are the eight embedded WebP sprite partitions wired through `Telegram/Resources/qrc/emoji_1.qrc` … `emoji_8.qrc` and included by `Telegram/CMakeLists.txt`. They are presentation data for the canonical emoji rendering pipeline, not message identity.

Orders 287-290 are the four set previews wired by `emoji_preview.qrc`. `Telegram/SourceFiles/chat_helpers/emoji_sets_manager.cpp` binds them through `PreviewPath`/`kSets` to Mac, Android, Twemoji and JoyPixels choices. The manager owns the `Available -> Loading -> Ready -> Active` progression, CloudBlob download progress, unpack/remove cleanup and stale switching fences.

Fabushi semantic adaptation: one canonical emoji renderer remains shared by Composer/Transcript; set preference belongs under one Settings/Appearance owner. The Telegram QRC/CloudBlob packaging and Telegram image bytes are not the target architecture and are not copied by this read credit.

## 291-336: offline HTML export representation

`Telegram/Resources/qrc/telegram/export.qrc` embeds `css/style.css`, all 292-335 PNGs and `js/script.js`. `Telegram/SourceFiles/export/output/export_output_html.cpp` emits the stylesheet link, copies the static resource set, and calls the script behaviors for generated offline HTML (including custom-emoji fallback notices).

The stylesheet itself references the section/media/back assets, including HiDPI variants. These files therefore form one static **export representation** responsibility. They do not own live Conversation/Message state and cannot be used as evidence for a live Telegram-shaped UI root.

Fabushi semantic adaptation: a single canonical user-data export pipeline must render from canonical Fabushi Conversation/Message truth, use Fabushi-neutral assets/tokens, remain accessible and secure offline, and never become a second message store.
