## Narrow source responsibility

**Proposed responsibility ID: `FBCP-CALL-SCOPE-001`**, under existing capability `CALL-REALTIME`: preserve the caller-selected direct peer and authenticated account as the call's identity context; a separate readable context must not authorize a different remote peer.

The directly observed chain is:

`TopBarWidget::call(_activeChat.key.peer()->asUser())` → `Instance::startOutgoingCall(user, args)` → successful permission callback → `Instance::createCall(user, ...)` → `Call(delegate, user, ...)` → `refreshDhConfig` / `Call::start` → `Call::startOutgoing` → `MTPphone_RequestCall(_user->inputUser(), ...)`.

- The top-bar entry obtains the peer from the active chat; the menu supplies video/confirmation choices, not a separate participant list. `startOutgoingCall` checks current-call activation and the peer's private-call status, captures the same `user` across the permission callback, rechecks current-call activation on success, and creates the call for that user. These are client behavior observations, not proof of Telegram server authorization.
- `Call` retains `const not_null<UserData*> _user`; its request sender is initialized from that user's session. `createCall` binds account session-change cleanup to the call lifetime. Current-call replacement hangs up the previous call. Destruction checks exact current-call object ownership. The redial path retains `_user` and refreshes DH configuration only for the still-current call.
- `Instance::handleCallUpdate` and `handleSignalingData` fence ordinary dispatch by the call's account session. `Call::handleUpdate` checks IDs in relevant update variants. `checkCallCommonFields` checks access hash and derives expected admin/participant IDs from call direction, `_user`, and `_user->session().userId()`; a mismatch fails the call. Accepted/confirmed call handling invokes the common checks; confirmed calls also check the key fingerprint. **Do not claim every response independently applies this full check**: the initial request response expects `phoneCallWaiting`, installs its ID/access hash, and follows the waiting-state path.
- Permission acquisition requests microphone, then camera when video is requested. A denied path does not invoke the success callback; existing calls can be hung up and system settings offered. DH/network or typed response failures route into failure/cleanup. `finish` handles a still-pending request by recording deferred finish plus a timeout, then uses the eventual call ID/access hash for discard. Discard completion/failure uses guarded callbacks; terminal state transitions prevent failed-call resurrection. These are bounded source observations, not an exhaustive race/lifetime proof.

At H, `create_call_session` first calls `read_human_conversation_transcript(scope_id)` (which proves a readable Human conversation containing the local identity), then independently derives `peer` from the request's normalized participant set. It posts that peer and finally stores the request's scope and participants. Existing `sync_human_calls` derives a canonical conversation from the remote peer and rejects the resulting durable scope mismatch.

The repair belongs in **the existing `ProductionSessionWorkers::create_call_session` Native branch**, using current metadata obtained through `open_human_conversation_db_owner`; it must not teach the call store or UI to invent conversation membership. A well-formed stored direct pair must contain exactly two distinct valid Human IDs including the authenticated local identity. The normalized request must equal that pair before a Native request or durable call write. When both validated pairs contain the same local identity and exactly one other member, equality of their selected peer is equivalent to exact pair equality. Retain request normalization/order compatibility, the existing credential-user and new-call response checks, and the current local non-Native path.

This exact-pair admission rule is a **Fabushi-specific adaptation** of upstream selected-peer/call ownership.
