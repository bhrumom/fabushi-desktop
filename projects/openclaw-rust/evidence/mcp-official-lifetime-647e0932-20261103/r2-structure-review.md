## R2 oracle and native-promise continuation order

The supplemental case at `mcp-runtime.contract.test.ts:2191–2257` reaches a different boundary from the retained default-chain final-scope-await case at 2162–2189. It constructs real `OfficialMcpService` instances and controls only the public scope/read/write/fetch I/O ports. It neither replaces `scope()`, `mutate()`, `requireActive()` nor modifies their prototype. Its scope port is deliberately non-async and returns the exact native deferred `Promise<string>` created by the existing helper at 122–129. No wrapper promise or thenable assimilation changes the intended reaction order.

The source establishes this schedule:

1. The old service reads its initial stored image. That controlled read arms the next scope lookup (2215–2218), so the hold occurs at the mutation's final scope lookup after its state read/change.
2. The controlled scope port registers its completion reaction on `finalScope.promise` before returning that same promise to the real `scope()` await (2202–2213). The old operation then remains held.
3. The replacement real service, using the same account hash and same stored string, completes a write first. The test asserts exactly one replacement write, its replacement token, and captures the exact committed bytes (2242–2245).
4. Releasing the native promise enqueues the previously registered I/O reaction before `scope()`'s await continuation. The I/O reaction queues retirement as a microtask. `scope()`'s continuation is already ahead of that retirement task, so its post-await `requireActive()` runs while active and the scope promise fulfills.
5. Fulfilling the scope promise queues the awaiting mutation continuation after the already-queued retirement microtask. Retirement therefore sets the real disposed latch before the mutation resumes at service line 69/72. The explicit final `requireActive()` refuses the write.

This ordering uses causal I/O notification and FIFO promise/microtask scheduling. It does not guess elapsed time, count a fixed number of promise turns, depend on a sleep, or patch the production guard. The timeout is a bounded failure guard, not the ordering oracle. The additional `retirementObserved` wait observes retirement; it does not authorize the write or supply its rejection.

The source counterfactual is specific and falsifiable: remove only the final `this.requireActive()` at `official-mcp-service.ts:72`, retaining both `scope()` checks. Under the authored schedule, both scope checks have already passed before retirement, and the old mutation resumes with equal account scope and an old in-memory image. It can then enter its write port; the operation would fail the required disposed rejection and zero-old-write/exact-byte assertions. This is a source counterfactual, not a claim that I ran a mutation test.

The fixture records old writes at actual write-port entry, demands `oldWrites === []`, and compares the full stored string to the replacement's captured bytes (2248–2250). A current same-account replacement must first write successfully. Thus silence is not enough to pass, and a newly created account identity cannot conceal a stale overwrite. The `finally` resolves the owned hold, settles the owned operation, and disposes both services (2251–2255); no global state or timer is installed by this supplemental case.
