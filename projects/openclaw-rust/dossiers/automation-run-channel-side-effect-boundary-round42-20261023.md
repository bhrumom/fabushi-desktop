## New evidence 1 — Transcript acceptance and Runner lease do not carry backend UUID to tools

1. `source/host/app/src/main.rs` blob `8e19361b3b278d085927a84ea4c8ce8c3fe3de80`, L3598–3688: `run_local_automation_turn` receives agent/automation/name/prompt, constructs fresh `automation-<UUIDv4>` stream and `automation:<agent>:<automation>:<UUIDv4>` client nonce; `automationWake` includes ID/name, not `runUuid`. It calls `transcript_runtime.accept_routed_send` and then `start_routed_provider_task` with that fresh stream. The `RoutedSendAcceptance.duplicate` return is not inspected at this call site.
2. `source/host/src/extensions/transcript/production_runtime.rs` blob `249133724863295b2992e89f168139679959c93a`, L565–572/L614–635/L650–808: the persistent nonce ledger and active queue admit by `clientNonce`, and the new routing lease is indexed by `streamId`. Coalesced/duplicate acceptance returns `duplicate=true` **without creating a new lease**. The dispatch path creates the new per-stream lease and returns `duplicate=false`. `source/host/src/extensions/transcript/send_pipeline.rs` blob `12f58e2923cd909b9564b99e0a6393955a0945e0`, L111–165, uses `HOST_ACCOUNT_SLOT` + nonce + input digest. `prompt_acceptance_ledger.rs` blob `2b9c15f8ce8f161dee62bd7502ddd56cda6c4fce`, L172–173/L212–249, keys stored records by `(account_slot,client_nonce)`, not by Sand run UUID.
3. **Important compensating boundary**: `main.rs` L5179–5203 requires `transcript_runtime.require_routed_turn_lease(agentId,streamId)` before routing provider execution. Thus reusing an identical nonce without a lease is *not* shown to run a second Runner; do not claim that merely ignoring `duplicate` bypasses the lease. Rather, the actual automation producer uses a new nonce and stream per invocation, so an upstream same-`runUuid` redelivery that passes run-store admission can acquire a different valid lease. This is a *possible* replay path; no occurrence has been observed here.

## New evidence 3 — concrete `send_message` external channel consumer and failure window

7. `source/host/src/runner/tools/send_message_tool.rs` blob `2ae0c6d1bac8f8cd93b9a4ed52f1f8da423c76de`, L386–457: the first-party `SendMessageToolBridge` validates input, emits initial tool interaction, then calls `self.sink.send_message(message,timestamp_ms,tool_call_id)` and reports success only from the sink's return. `CountingSendMessageSink` L112–175 increments its in-process counter whenever delegate `send_message` returns `Ok` (no independently observed remote channel receipt).
8. **New actual consumer**: `source/host/app/src/main.rs` L633–665/L780–868 and L7374–7396 instantiate `ProductionSendMessageSink` wrapped in `CountingSendMessageSink`. For a `channel`-bearing message, the production sink **first spawns a detached thread** calling the Host lane method `deliverToChannel` with only `{agentId,addressToken,message}`. It does **not** include either `tool_call_id`, `streamId`, or Sand `runUuid` in that call. The sink then independently calls `append_generated_send_message_entry`, publishes the transcript event, and returns `Ok(Some(local_entry_id))`. The async channel failure is logged by the detached thread and does not turn that already returned local message into an authoritative delivered receipt.
9. **Second async boundary**: `main.rs` L8977–9039 `UnifiedGatewayApi::call("deliverToChannel",...)` validates agent/address/message, builds the outbound, launches a **second detached channel-delivery worker** and immediately returns `{"queued":true}` on successful spawn. The worker calls `HostChannelDelivery.deliver`; on error it enqueues an error tray/background failure wake. Neither this gateway method nor the worker receives a stable backend run UUID or originating tool-call ID. A `queued` acknowledgement proves only local worker scheduling, not provider delivery. It also is not awaited by the original Runner tool call.
10. `source/host/src/connectors/channel_delivery.rs` blob `67a2766a16d5f59a664e9b4d9c1d7fb3dbcacc5d`, L10–17/L36–72: the current abstract shipping boundary is `ChannelDeliveryPort::deliver(&self,agent_id,address_token,message) -> Result<(),String>`, backed by `HostChannelDelivery`'s pluggable port. It has no `runUuid`, tool-call ID, request/attempt identity, or durable outcome key parameter. A concrete plugin/provider *might* implement some separate, undocumented deduplication based on other data; no such protection is established by this examined port contract. Do not infer that a registered external port is necessarily the default `UnregisteredChannelDeliveryPort`.
11. **Falsifiable ordering/failure interleaving** (not observed): first asynchronous channel dispatch may deliver successfully while local `append_generated_send_message_entry` fails, or after the local transcript succeeds but before its remote receipt is known. The Runner receives a local error/success unrelated to authoritative remote settlement. If the same backend `runUuid` is subsequently admitted with newly generated stream/nonce, no reviewed layer here compares the two external mutation operations by that backend ID. This is a credible duplicate-or-unknown-outcome *risk*, not evidence of an actual duplicate.
