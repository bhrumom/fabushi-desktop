## 1. New independently traceable findings

### R53-RESOURCE-01 — single unscoped renderer resource outlives account changes

- ProductionRenderer.tsx blob af8a83a8dd7cf1444474889ce3e64fe796a7d458 L525-L555 constructs createAutoReviewInstructionsResource once from DesktopBridge. It holds one closure-wide snapshot and listener set; its interface only has snapshots.get/subscribe, load, setInstructions. It has **no accountSlot, account generation, invalidate, reset or dispose**.
- L783 creates this resource with React useState initializer, not keyed to the logged-in account. L2082-L2104 passes the same resource into every createAutoReviewApprovalActions instance. L2164-L2170 disposes individual actions when the account:agent string changes, and L2189-L2203 disposes actions on mount cleanup, but neither path invalidates the instruction resource's cached snapshot nor cancels its pending get/set.
- The component *does* know the account lifetime: L1040-L1043 has accountIdentityRef/accountScopeGenerationRef; L3242-L3250 increments accountScopeGenerationRef when account identity changes, and L3255-L3303 resets many other account-owned projections. No corresponding AutoReview instructions resource reset is present in these inspected production paths.
- DesktopBridge interface blob 4f7e088e93008ab1e53736afecf0772bf6c5e01b L555-L560 exposes get/set of instruction values only, without account/version/Host receipt metadata.

Consequence (conditional source-level interleaving, **not an observed incident**): a get started under account A may complete after the renderer transitions to B and populate this unscoped resource with A's settings. An older action might then append A's proposedRule and issue set through the current Electron account context. Action dispose only fences its own *publication* at auto-review-actions.ts L185-L207; earlier asynchronous side effects remain possible, as separately described in round52. A successful B get in normal serial flow can replace stale values, so cross-account contamination is **not claimed as proven**.

### R53-RESOURCE-02 — asynchronous load/set results may reorder one resource's snapshot

- ProductionRenderer.tsx L538-L549 starts an async bridge.autoReviewInstructions.get and unconditionally assigns its result to the shared snapshot upon completion. L551-L554 awaits bridge.autoReviewInstructions.set and likewise unconditionally assigns its result. Neither operation carries a request sequence/revision or rechecks scope; a late response can overwrite the snapshot from a newer operation.
- auto-review-actions.ts blob 96a427f0f2536c9f25aaa4035faf61e3cec9e0dc L148-L156 awaits load(), immediately uses snapshots.get(), then sets appended allow instructions; L92-L103 performs read-modify-write over the supplied list. Concurrent actions can therefore be probed for stale read, last-writer-wins or lost-rule outcomes. This is a **testable race hypothesis**, not a measured failure.
- The resource's cached snapshot is a renderer projection, not the authoritative Host execution policy. Failure to distinguish it from the persisted Electron settings or Host settings can lead to misleading UI claims.
