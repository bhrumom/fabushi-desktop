## 3. Pairing state and falsifiable unknown-outcome oracles

1. **PAIR-R19-01, pending request identity.** `device-pairing-core.kernel.ts:41–190`: same public key/browser origin/role with identical or subset roles+scopes refreshes the *same* pending requestId; it preserves original `ts` queue ordering and only refreshes TTL through `refreshedAtMs`. An escalation or incompatible request supersedes pending IDs before saving. Negative: reconnect cannot reorder `--latest` approvals or re-use an obsolete/superseded requestId as fresh approval authority.
2. **PAIR-R19-02, transactional approval and scope.** `device-pairing-approval.kernel.ts:178–305`: approval loads an actual pending row, requests mutation admission, rejects scope outside requested roles and missing caller operator scope; the trusted ingress same-key exception is not authorization for key-changing repair. `:112–141` stores paired token+pending deletion together. `:306–382` treats bootstrap as a separately bounded grant. Negative: key mismatch, absent pending row or insufficient scope cannot approve.
3. **PAIR-R19-03, token and node generation.** `device-pairing-approval.kernel.ts:281–305,342–381`, `device-pairing-token-utils.ts:14–43`, `device-pairing-identity.ts:87–199`: normal reapproval generates a fresh bearer while optionally retaining the existing issuer; bootstrap approval rotates with different rules. The authenticated token identity includes public key, device creation, bearer/rotation/revocation facts; current continuation must match live token, durable approved role and whole approved scope ceiling. Node capabilities have their own generation. Negative: a previously approved operator, removed node role, rotated token, changed key or older node generation cannot continue acting after new read.
4. **PAIR-R19-04, native COMMIT is not reply delivery.** `device-pairing-worker.ts:98–219` installs a committed receipt before normal completion, even through result/callback errors; missing settlement can block publication. `device-pairing-worker.test.ts@ce6f54087111c5df4aa7b2cf97663cd4fe6fffc1:534–611` distinguishes three injected outcomes: pre-COMMIT policy revocation leaves database unchanged; reply lost/callback throws *after* COMMIT leave narrowed scopes and new bearer persisted. `sqlite-worker-operation-admission.test.ts@2ce87b63c700ee3d5f6f2d3487d57ee6dabd5760:351–408,482–575` preserves native COMMIT facts across unknown settlement or notification failure. Negative: error/timeout/cancel/socket loss cannot prove rollback and cannot trigger duplicate approval.
5. **PAIR-R19-05, current-state reconcile before authorized retry.** `device-pairing-store-readonly.ts:19–77,114–166` separates current committed authority reads from inherited inspection snapshots. `openclaw-state-db-readonly.ts:482–630` exits inherited inspection context for `current` and rechecks admission. `device-pairing-publication.ts:74–170,196–261` uses revision, identity, epoch, committed receipt and fail-closed blocked state. An unknown outcome requires re-read of `requestId`, device/key, pending+paired status, pairing revision, exact role/scope, token issuer/bearer generation and node generation from the authoritative surviving owner. If committed: do not replay. If revoked/replaced: reject old grant. If conclusively not entered/not committed **and** current authority newly approved: retry under a fresh admitted operation. Absence of pending alone is inconclusive (success, rejection, expiry and supersession can all remove it).
6. **PAIR-R19-06, read and cleanup ownership.** `openclaw-state-read-operation.ts:65–220,221–318` joins task completion, transport close, private snapshot cleanup, retained source release and caller cancellation; `openclaw-state-read-worker.ts:177–456` captures worker generation and closes queued task resources; `sqlite-readonly-location-cleanup.ts:131–249,296–470,500–586` forbids deletion while active retained readers own bytes. `sqlite-readonly-location.ts:75–223,290–455,487–770` rejects source/sidecar changes, stages private snapshots and performs cleanup. Negative: an abandoned reader, failed native close, stale source identity or failed snapshot removal cannot be rewritten as a safe completed read or a mutation rollback.

This is a **source behavior/oracle specification**, not evidence that Fabushi implements these statements, not an executable test, and not permission for speculative retry.
