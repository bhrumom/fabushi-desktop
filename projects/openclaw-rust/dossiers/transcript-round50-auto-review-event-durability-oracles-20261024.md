## Newly isolated source-backed failure boundary: AutoReview event notification can outrun durable transcript state
At fixed subject `source/host/src/extensions/auto_review/auto_review_service.rs` blob `113d452894668480eb4ae48c8c0183fd6e24e124`, `handle_event` calls `persist_event(event)` (around L431), then emits `on_update` (L439-459). `persist_event` has no Result return (L466) and ignores errors from `append_agent_transcript_entries` on Created (L486) and `update_agent_transcript_entry` on Resolved/Expired (L522-526); read failures and missing entries cause early return only *from persist_event*. This means a live subscriber can receive a Created or Resolved event even though persistence failed, and a subsequent restart/snapshot need not reproduce the notified state. This is a conditional source-level failure contract, not an executed failure injection or a proven production incident. The in-memory settled-id list (L527 onward) is not itself durable approval status.

**Falsifiable oracle AR-EVENT-DURABLE-50**: Arrange a live controller for agent A and a pending request R; inject a session append error at Created; capture on_update, transcript storage, and post-restart replay. Then resolve R with transcript update error; compare live Resolved signal with persisted approval status after fresh Host/session initialization. Pass requires a documented authoritative failure/reconcile outcome and no false durable terminal assertion. Execute only in GitHub Actions after scoped G01/G02 and owner/oracle independent admission.

## Boundary sharpening with precise inputs (not run)
- **AR-ENTRY-BIND-50**: register controller A with pending request R and matching entry EA, invoke `resolve_approval_for_entry(R, approved, agent B, EB)` where B != A; separately B=A and EB != EA; observe controller A state and B transcript. The live-controller predicate in `auto_review_service.rs` L221-248 currently searches any binding by request ID, while the expiry counterpart at L288-309 includes agent ID. Expected security invariant: resolution should require the canonical agent and intended entry binding; request-ID-only collision or wrong-context mutation must not authorize execution. No exploit claim without controlled evidence.
- **WIDGET-ROLLBACK-CAS-50**: for one entry W initially unanswered, block send of attempt 1 after `respondedValue=alpha` is stamped, arrange a later independent update (or competing response attempt) with `respondedValue=beta`, make first send fail, and release its rollback. Inspect final durable value and emitted update ordering. `widget_responses.rs` blob `97b4b47b61b3c2cd18d381758ebec2640714f1d3` L240-297 has unconditioned removal; the race interleaving may need a forced storage update because ordinary second response is guarded. Pass requires failed attempt 1 never clears a different committed attempt/revision.
- **GROUP-INSERT-COUNT-50**: create room entry ID collision to force lower storage `INSERT OR IGNORE` to affect zero rows; drive `append_member_message` and inspect stored room history, shared publish, observer notifications and `posted_messages` count. `send_group_fanout.rs` blob `f67898a1c93dffdaf81d38349bb454300ae56ea0` L64-93 discards returned insertion count; no zero-row success should be externally reported.
- **GROUP-EPOCH-LATE-50**: start a group member executor at epoch E, block its completion, advance room epoch to E+1, return a message, inspect `post_member_message`, shared-room publish, room transcript, UI subscriber and count. `group_chat_orchestrator.rs` blob `5c29378ec40b1eb365be9c27f0f32c730d07a1ed` checks `is_current` around L64/74 but posts at L84 without a post-executor check. Pass requires no post-cancel stale publication.
