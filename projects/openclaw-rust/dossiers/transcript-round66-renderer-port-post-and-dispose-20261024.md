## New distinct narrow facts

**R66-RENDERER-POST-29 — Renderer data-port `postMessage` synchronous-throw cleanup is not identical to MainData's swallowed post exception.**

- Exact target `frontend/src/production/coordinator-client.ts`, blob `f120b9f600861560409d9a9cac6487cb5ec79e63`, L157–164: `call` awaits `currentReady`, allocates `r-N`, inserts `pending`, then invokes `port.postMessage` **without try/finally deleting the pending entry**. If this renderer-side `postMessage` throws synchronously, the caller receives rejection through the async function, but the pending map retains an orphaned request until `rejectCalls` or matching reply. This is distinct from R65's Electron MainData `leg-post` swallowing and indefinitely pending caller: here the initial awaiting caller can reject, while private pending entry remains. No evidence yet that the renderer endpoint throws during normal account transition.
- L80–95: active-port disconnect rejects all pending and clears the map; L135–151: replacing an already installed live port invokes `rejectCalls("coordinator session replaced")`, then closes old port. L182–190: explicit `dispose` invokes shutdown `postMessage` **before** `claim.release()`, `rejectCalls` and `port.close()`. A synchronous throw from shutdown post therefore exits disposal before that cleanup. This is a separate testable exception-safety gap, not proof that cleanup never happens through another independent close/host teardown.
- L135–155 `onPort` invokes `nextPort.postMessage(hello)` after listeners/start but before returning; a synchronous throw there can likewise leave an adopted port without completed hello; the independently registered `close` handler, if raised, calls `disconnect`. The source does not establish whether Electron always emits close after such a throw.
- Counterexample/oracles: provide a fake transferred Renderer Data port whose first request post throws, verify `call` rejects and subsequent explicit `close`/port replacement reclaims pending; fake shutdown post throwing during `dispose`, assert `claim.release` and pending cancellation still occur (currently not guaranteed by source); force hello-post failure and check claim/port recovery. Distinguish orphaned metadata from already-executed external side effects. Because no scoped G01/G02 and owner/oracle admission, **do not run Actions**.

**R66-PERMISSION-MICROTASK-30 — independent microtask scheduling and disposed-state gate on the actual bridge write.**

- Exact target `frontend/src/recovered/features/permissions/local-tool/store.ts`, blob `a1a59201b843c433d619c08d9c18a08664c735a1`, L166–185: `setPermission` increments local versions synchronously, then uses `Promise.resolve().then(() => bridge.set(requested))` **with no `disposed` test inside this microtask**. Therefore a caller can invoke `setPermission`, synchronously dispose the store before the microtask executes (L193–201), and the already-queued callback nevertheless invokes the durable bridge setter. Local version/disposed checks guard only L174–183 snapshot publishing. This sharpens, but does not duplicate, R65's broader already-dispatched bridge-write cancellation concern. `recordApproval` L187–189 directly delegates to the bridge without an ownership/disposed check; no microtask staging is asserted for it.
- Exact target `frontend/src/recovered/features/permissions/local-tool/view.tsx`, blob `aaff6101b5ab2a3cb85390471083c4359b6fad31`, L93–110: Always/Never persist before host RPC, allow-once records separate approval first; L113–128 starts async action and only updates UI state on completion. There is no account-generation check across the awaits. Conditional A-to-B crossing remains subject to actual account transition and Host authorization, not established acceptance of stale A approval by B.
- Oracle: invoke `setPermission("always")`, call `dispose()` in the same synchronous turn, flush JS microtasks, count `bridge.set` invocations and persisted writes; separately drive A pending UI click, hold/release bridge and reconcile B connection, assert that no A-origin persistence or send targets B account scope. These are **proposed falsifiers**, not passing tests.
