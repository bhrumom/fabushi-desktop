## R58-LOCAL-STALE-SWEEP-ORDER-06 — stale handling may mutate the real pending card before validating entryId

- source/host/src/extensions/transcript/widget_responses.rs blob 97b4b47b61b3c2cd18d381758ebec2640714f1d3 L395–423 first calls workers.expire_pending_local_tool_permission_asks(agentId, Some(requestId), None). When this returns nonempty, it only *then* optionally finds the user-provided entryId to emit an update and returns Retired. The is_local_tool_permission_entry(entry, entryId, requestId) matcher runs only in the **later** branch, after the expiration attempt returned empty.
- source/host/src/extensions/session/production.rs blob d2b455d19e7ee012f046227fd6eb4845669b7ee7 L1763–1776 delegates the expiration to pending_card_sweeps; source/host/src/extensions/session/pending_card_sweeps.rs blob 39513fb90cf7d22447a3fee90d759b29bacdb7b7 L51–99 selects persisted pending local-tool cards by requestId and timestamp, then mutates the entry using its **actual persisted entry id** at L87–92. There is no supplied entryId parameter at that layer.
- Therefore, if the controller no longer has the live request but the agent transcript still has a pending card for requestId=R at entryId=E, a stale resolve command using requestId=R and **a different supplied entryId=W** can expire E before the handler checks or emits for W. The requestId must still match: this is not a claim that an arbitrary unknown request can mutate an arbitrary card. The optional update event may be sent for W rather than E if W exists.
- source/host/tests/widget_responses_local_tool_permission_contract.rs blob 0a6b6d0853f054cbd906f55dd1b12fa33fd7b47d L36–85 covers correct (E,R) expiration, repeat success and missing E only *after* the correct card is already settled. ## R58-LOCAL-LOST-DECISION-FANOUT-07 — global pending-card settlement can follow a losing same-ID HTTP decision

- The already recorded R58 same-request race showed that a losing concurrent Always/Never resolve can persist standing policy and call note_permission_changed after its own settle_pending returns None. A distinct **cross-request scope** is visible in source/host/src/extensions/local_tool_permission/local_tool_permission_controller.rs blob 2e7722129582974b7cdbacc058fca3dae490ba2c L603–682: note_permission_changed reads the current effective global permission and, when it is not Ask, collects **all** pending_by_key values without restricting to the resolving requestId or agentId. It settles each as Always/Never (or expires stale epochs), and may retire every retained approval. The originating resolve at L808–816 does not gate notification on settled.is_some().
- Thus a losing decision's successful standing-policy write can fan out effects to other concurrently pending agents/requests. This is more specific than merely changing future default policy or settling the same request: cross-agent pending request settlement is a separate observable lifecycle effect. Such fanout may be intentional for a **valid** global policy transition, but must not be attributed to a losing/invalid approval. The existence of a complete HTTP interleaving is source-supported, not executable evidence.

Unrun falsifier FANOUT-58: pending R1 for agent A and R2 for agent B; race two decisions for R1 with controlled barriers before settings.persist and settle_pending, verify R2 disposition, agent-specific events and approvals, final global effective permission, disk bytes and restart. Include duplicate same-choice and conflicting choices; compare winner-only expected side effects.
