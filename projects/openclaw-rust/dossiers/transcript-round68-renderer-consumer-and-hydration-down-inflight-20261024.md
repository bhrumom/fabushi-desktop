4. **New consumer-level consequence:** `frontend/src/recovered/features/root-resilience/connection-state.ts` blob `c8de518fbc65f1ae03b0d58f8be64f501e054bb9` L117–185 keeps one `retryInFlight`; `runRetry` assigns the `source.retry()` promise to it and clears it only in that promise's `.finally` L174–181. The controller is held in Renderer state across normal account status changes. Therefore a malformed reply for account A's roster can conditionally latch that controller's explicit retry path across port replacement and A→B account status, until the outstanding promise is independently settled or the controller is recreated. This is **not** proof B Host accepts A work or that the entire UI is unrecoverable: a separately triggered roster request may still run.

## R68-ONBOARDING-DOWN-INFLIGHT-35 — ordinary transport-down does not fence a started mirror hydration

3. `source/shared/host-settings-field.ts` blob `d42c80580522a85459220303771d2cdf98a0e786` L7: `absorbFromBox` snapshots only `WriteEpoch`, awaits the Box read, then checks only `#writes.isStale(readAt)`.
