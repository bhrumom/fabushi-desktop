## 3. R27-FDN-02: logout/revoke and asynchronous account-change boundary

Account service L95-135 holds operationEpoch, logoutInProgress and activeOperations; login L545-552 increments epoch, aborts old login and tracks new login. Current session/refresh L390-460 checks epoch between steps. Logout L622-659 increments epoch, aborts login, awaits a snapshot of tracked operations, clears stored session and BOTH Host files, stops remote heartbeat, and optionally makes a non-awaited fire-and-forget /api/auth/logout request for the selected stored session. revokeForAccountRefusal delegates to logout. These existing fences are real; do not report them missing. A prior CI bootstrap is not incorrectly replaced with an unrelated stored user for logout.

Heartbeat L261-310 validates the secure-store secret, first-party response and captured account identity + epoch; failure invalidates local registered identity and clears Host device file. But the inspected logout path does NOT remove the persistent per-account/device secure-store deviceSecret and does NOT send/await a distinct Remote Computer unregister. Token/session revocation is therefore not established as server device deauthorization; retention could be intentional for re-login, so require product policy and real endpoint oracle rather than assuming a vulnerability.

Crucial ordering question: ensureRemoteComputerRegistration L318-350 shares one registration promise and performs readSecret -> optional writeSecret -> network register -> Host device-file write -> identity assignment WITHOUT an operationEpoch guard immediately before the final file write. Callers check epoch after awaited settlement, and logout awaits tracked operations; a new login increments epoch but does not drain prior active operations before it starts. Thus a late registration from A racing with B login/credential replacement is a concrete missing local guard to challenge via deterministic A->B interleaving. Its actual outcome, backend refusal and account-side cleanup have not been reproduced. Do not call it a proven exploit or disable existing fences without reviewed design.
