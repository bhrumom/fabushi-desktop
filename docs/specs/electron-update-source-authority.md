## Context and scope

At Desktop `8ce0a9a43b7fe94df2ec2085399fe65a57343577`, shipping `entry.ts` selects `createElectronProductionUpdaterInstallerBinding`, whose existing `createProductionUpdaterInstallerBinding` calls `createUpdateServiceWiring` and starts `SandUpdateService`. The wiring reads optional `SAND_UPDATE_FEED_BASE_URL`; the service otherwise selects the built-in `https://api2.cursor.sh/updates` from `update-feed.ts`. Startup, periodic, manual and minimum-version checks can therefore send the machine identifier to that historical third-party default.

This batch removes that implicit authority and preserves an explicitly configured approved feed through the same service. It does not claim an operational Fabushi update endpoint, authorize deployment/publication, replace the updater, change user-data schemas, or complete signing/package/install/rollback acceptance. Fixed source U remains `f985723b552b30fe1c17d377d57f44e61a15a8c4`. CSI-R1/3/5/6 and the latest round-21 instruction govern this intentional adaptation of the recovered updater.

## Requirements and behavior

- **EUS-01 — Explicit source.** No built-in feed URL. `FABUSHI_UPDATE_FEED_BASE_URL` is primary; `SAND_UPDATE_FEED_BASE_URL` remains an explicit compatibility configuration only when the primary variable is absent. Present-empty or invalid primary configuration must not fall back to the compatibility value. Configuration is trusted main-process startup input, never renderer input. No feed is persisted to Settings or inferred from account credentials.
- **EUS-02 — Approved origin.** Reuse `source/shared/node/fabushi-service-origin.ts::normalizeFabushiApiBaseUrl` to validate the explicit URL's origin. Production/isolated CI HTTPS and loopback HTTP/HTTPS follow that existing authority; no arbitrary foreign host or historical Cursor origin is accepted. Preserve a configured path prefix for the existing feed wire protocol. Reject credentials, query, fragment, malformed URLs and remote HTTP. Reject before a fetch; error/status/telemetry must not echo the rejected raw value. No metadata redirect may escape the selected origin: manifest requests use `redirect: "error"`.
- **EUS-03 — Fail closed throughout lifecycle.** The service independently resolves its `feedBaseUrl`, even when constructed without production wiring. Missing/blank source yields `update-source-unconfigured`; invalid or unapproved source yields `update-source-invalid`. The existing explicit environment, Lab, packaging and platform disabled reasons retain precedence. Disabled startup/manual/periodic/track-change/minimum-version/backend checks do not fetch or install and do not arm timers. `applyDisabledReason(null)` cannot bypass source configuration. Disposal prevents a new check. Enabling an approved source requires reconstructing the service from the updated startup configuration.
- **EUS-04 — Preserve behavior and recovery.** Valid explicit configuration retains current track selection, requests, manifest parsing, download/signature/staging/install owners, safe relaunch and cancellation. Existing `sand-update-apply-marker.json` format and path, settings keys, and user/session data stay unchanged. Startup still settles a previous apply marker through the existing settlement owner even when updates are disabled; disabling source must not skip the recovery receipt or invent a successful installation. Normal settlement clears only its own marker. No user-data cleanup or automatic rollback to the historical feed.
- **EUS-05 — Observable state.** Existing update status IPC and Settings projection represent the two source-disabled reasons with fixed user-facing messages. Add non-retryable telemetry causes for these reasons. HTTP status errors omit request URLs, which contain the machine identifier. No new updater IPC or service authority is added.
- **EUS-06 — Evidence.** Behavior tests execute the real service/wiring, source resolver, telemetry, Settings projection and marker store with controlled fetch/clock/platform ports. All executable checks run only in GitHub Actions at the submitted exact H. Source reading, authored tests, execution and independent acceptance remain distinct in the canonical ledger/RTM.

## Implementation and interfaces

Extend existing `update-feed.ts` with `configuredUpdateFeedBaseUrl(env)` for raw variable precedence and `resolveUpdateFeedSource(raw)` for validated source/disabled reason. Reuse the shared origin policy; do not create a second allowlist. The service stores this immutable resolution, combines its reason with existing runtime gates, and consumes only its validated base URL. Production wiring forwards the explicit raw choice and the injected platform; the composition's existing dev-feed override recognizes the same primary/compatibility choice. New disabled reason literals are carried through the existing typed renderer contract and Settings message function. No account credential or schema change is required.

`start()` first runs the unchanged apply-marker settlement and then handles the source gate. A valid feed follows the existing idle/checking/available/downloading/staging/ready transitions. A missing/invalid feed stays disabled when manual checks, track changes or remote experiment callbacks arrive. An approved feed failure returns through the existing idle/error or staged-ready recovery, without selecting another feed. Existing user-selected track and idle-update settings remain writable and recoverable while disabled.

## Round 22 — Windows publisher authority (2026-11-03 Asia/Shanghai)

At exact base `8f089dd8640dacb4ec39105aa6d43e4c547ac5a2`, the same shipping wiring constructs `SandWindowsInstaller` without a signer override. Its built-in `Anysphere, Inc.` / `Anysphere` common-name list therefore authorizes a historical third-party publisher. Neither `desktop/package.json` nor the inspected release configuration establishes an authorized Fabushi Windows certificate. Product/author names and a valid Windows certificate chain are not publisher authorization.

The existing Windows installer, update service, Settings status and apply-marker store remain the sole owners. This amendment removes implicit publisher authority and adds explicit certificate authorization; it does not invent a legal identity, issue a certificate, deploy a feed, sign/release a package or alter existing user data.

- **EUS-WIN-01 — Explicit immutable authorization.** Production main-process wiring reads only `FABUSHI_WINDOWS_UPDATE_PUBLISHERS_JSON`. The value is a nonempty JSON array of at most 16 objects, each with exactly `subject` and `certificateSha256`. Subject is the exact nonblank Windows X.509 subject, without surrounding whitespace or C0/C1 control characters (U+0000–U+001F and U+007F–U+009F); SHA-256 is 64 hexadecimal characters, normalized to lowercase. Duplicate certificate pins, malformed entries, unknown fields or partial configuration reject the entire policy. Missing/blank input is `windows-publisher-unconfigured`; all other invalid input is `windows-publisher-invalid`. No common-name-only, Anysphere, legacy environment, package-name or renderer fallback exists. The installer snapshots and freezes the parsed policy; editing the original environment cannot alter a running instance.
- **EUS-WIN-02 — Native signature plus authorized certificate.** `verifySignature` requires Windows `Get-AuthenticodeSignature` status `Valid`, signature type `Authenticode`, and the exact subject and SHA-256 of `SignerCertificate.RawData` from the same configured entry. It never uses the timestamp certificate or SHA-1 thumbprint as publisher identity. Unconfigured/invalid policy, missing/malformed output, unsigned/untrusted/catalog signatures, certificate mismatch, native timeout/process failure and file-read failure reject with fixed errors that do not echo raw configuration, subject, PowerShell stderr or output. Literal paths stay correctly quoted. The child PowerShell process emits BOM-less UTF-8 so exact Unicode subjects survive a non-UTF-8 Windows console code page. The existing 30-second native probe timeout is retained.
- **EUS-WIN-03 — No admission bypass.** A Windows installer exposes its immutable disabled reason to the existing service. Constructor admission and later `applyDisabledReason(null)` include that reason after existing runtime gates and the feed gate. Disabled startup settles the existing marker first, then performs no timers, fetch, download, stage, quit or installer spawn. Non-Windows behavior and source-disabled precedence remain unchanged. Direct verifier use fails before a native probe when authority is absent. Direct install requires that this same installer instance successfully verified that exact path, and consumes that permission once.
- **EUS-WIN-04 — Bind verification to candidate bytes.** Hash the candidate before and after the native signature probe and require equality before granting a one-use install receipt. Any failed re-verification revokes the path's prior receipt. Immediately before spawning, synchronously stream the file through SHA-256 and compare it with the verified receipt; missing/changed files fail via the existing `onSpawnError` callback with no spawn. This detects ordinary/deterministic replacement, without claiming atomic exclusion of a hostile same-account hash-to-CreateProcess race. Actual Windows file-lock/process-launch behavior and real signed install/rollback remain release gates.
- **EUS-WIN-05 — Preserve recovery and projection.** Existing `staged -> requested -> spawned/spawn_failed -> restart settlement` ownership and the `sand-update-apply-marker.json` format/path stay unchanged. Failed authorization never marks a new version ready, never quits, and deletes only that rejected downloaded candidate; any previously valid staged candidate remains recoverable. Existing Settings keys remain writable. The two publisher-disabled reasons receive fixed Settings messages and distinct non-retryable telemetry codes, without a new IPC/configuration surface.
- **EUS-WIN-06 — Authorization evidence and verification.** Supplying syntactically valid configuration is not proof of formal publisher approval. Release qualification still requires an approval/provenance record naming the exact subject and certificate SHA-256, authorized rotation entries, the real signed executable and package hashes, native Windows chain/signature execution, and actual install/upgrade/rollback/recovery. This task supplies no production identity. Focused behavioral contracts execute the real installer, wiring, service, marker store, telemetry and Settings projection with explicit fixture certificates/native process ports; they cover denial, joint-pin matching, rotation, byte changes, one-use launch, failure, cancellation and restart. Only GitHub Actions may execute them, bound to the submitted exact H; fixture success is not signed-Windows-package acceptance.

Implementation remains in `win32-installer.ts`, `update-wiring.ts`, `sand-update-service.ts`, the existing status/telemetry/Settings types, and a neighboring `windows-publisher.contract.test.mjs`. Preserve the existing Electron/UI jobs and compile the actual entries. The canonical ledger, RTM and round receipt distinguish authored/executed contracts from G-RELEASE and independent ACCEPT.

The focused Windows Actions job also exercises the actual native probe using a short-lived, explicitly named CI-only code-signing certificate and an inert generated fixture executable. It adds that exact fixture certificate only to the runner's CurrentUser stores, signs the fixture, derives its test-only subject/SHA-256, and removes only that certificate in cleanup. The fixture executable is never launched. Required native cases include valid joint identity, wrong certificate/subject, unconfigured authority, unsigned/tampered input, catalog/invalid signature refusal where reachable, replacement before launch, and a Unicode subject under a controlled and observed CP437 startup prelude in the actual native process. The first ten native cases use the unmodified default launcher; the Unicode case adapter prepends only the initial encoding/proof before executing the production-generated script and returns actual native output, not a fabricated probe. These prove Windows API integration for controlled fixtures, not formal Fabushi publisher authorization or real application install/upgrade/rollback. No private key/certificate export is uploaded; evidence contains only nonsecret fixture identity and outcomes.

Operational enablement requires the release owner to provide the approved policy through trusted main-process startup configuration and restart. Rotation is explicit, with old/new certificate entries approved together; never learn a pin from a downloaded manifest or automatically trust the installed product's name. Rollback preserves the no-default boundary and existing recovery data. A code rollback may not silently reinstate third-party publisher trust.
