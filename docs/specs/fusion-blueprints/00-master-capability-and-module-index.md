## 1. 总纲与核心设计原则

### 1.1 核心使命与零遗漏铁律
本文件是 Fabushi 统一产品体验（Unified Fabushi Experience, UFX-001）的**权威全景总控索引**。它的核心目标是终结历史上由于局部视角导致的模块割裂、孤岛代码、虚假在线状态和断头调用链。

本索引必须达成两大零遗漏要求：
1. **OpenClaw 零遗漏**：100% 覆盖 OpenClaw 全源码范围的全部 32 个责任域（`OCRM-M01` 至 `OCRM-M32`，涵盖 77 个 `src` 子目录、176 个 `extensions`、50 个 `skills`、4 个 `custodian-skills`、24 个 `packages`、8 个 `apps` 及 2 个 `crates`），每一项能力均有明确的 Fabushi 目标落点与分卷蓝图归属。
2. **Telegram Desktop 零遗漏**：100% 覆盖 Telegram Desktop 源码精读与能力图谱全量 52 个能力域（`TCG-N01` 至 `TCG-N52`，涵盖 40 个顶层 `SourceFiles` 目录与 118 个核心子目录），消除历史遗留的 50+ 能力断点，将 IM 通信、群组、频道、富媒体、通话、动态、安全与原生网络完整吸收入 Fabushi 既有架构。

### 1.2 单一装配律（Single-Composition Law）
统一不是“将所有逻辑塞进一个巨石文件”，而是**每个产品概念在架构上必须且仅有一个 Canonical Root Composition**：
- **禁止建立平行世界**：严禁创建类似 `TelegramRuntime`、`TelegramCore`、`OpenClawRuntime`、`CommunicationCore` 等平行的二级应用或第二套会话数据库。
- **现存责任优先吸收（Existing-Owner-First）**：Telegram 与 OpenClaw 的所有功能必须沉淀到 Fabushi 既有的生产架构中（即 `frontend/src/production/`、`frontend/src/recovered/features/`、`source/host/`、`source/node-agent-coordinator/`、`native/mahayana-messaging/`）。
- **同一责任归属不等于同一文件（Same Owner != Same File）**：为了维护生产代码的高可读性与可维护性，遵循单一内聚模块 **200–600 行** 的预算控制，通过子组件与细分策略文件清晰拆分，但对外必须暴露单一权威 Context 或 Controller。

### 1.3 信息架构与 UI 视口层级（UI Information Architecture）
任何迁入的用户可见能力，必须严格按照用户的任务作用域（Task Scope）进行标准收敛，严禁凭空添加平行的顶层视窗或悬浮浮窗：
1. **一级左侧主导航轨（`FabushiPrimaryNavRail`）**：稳定的跨对象顶级产品域切换，包括 `chats`（会话）、`tasks`（任务/自动化中心）、`contacts`（通讯录/联系人）、`marketplace`（插件/MCP/Mini Apps）、`settings`（系统设置）。
2. **二级列表/集合过滤栏（`FabushiCollectionFilterBar` / `Sidebar`）**：当前域内的列表过滤与快速切换（如全部、未读、群组、频道、Bot/Agent、Topic 论坛话题等），统一收拢于单一会话列表。
3. **中央主舞台（`ConversationWorkspace`）**：
   - **单一顶部导航栏（`ConversationHeader`）**：消除 `activeIsHuman` 的分支割裂，为人机混合、纯人、纯 Agent、群组、频道提供唯一顶栏，包含当前对象元数据、状态指示、置顶横幅（Pinned Bar）、搜索、音视频呼叫入口与详情抽屉开关。
   - **核心消息流（`ConversationTranscript`）**：单一权威消息流，无缝承载文本消息、Markdown/代码卡片、思考流（Thinking Bubble）、工具调用进度、权限审批卡片、富媒体附件、投票（Poll）、待办（Todo）与系统通知。
4. **唯一权威输入台（`ConversationComposer`）**：消除双重输入器冲突。为人与 Agent 输入提供唯一输入框，集成附件上传、语音输入转写、中文输入法（IME）保护、草稿自动保存、流式中断按钮以及底部的工具栏动作扩展（投票、待办、发票直发等）。
5. **唯一右侧上下文详情栏（`ContextInspector`）**：彻底废除独立的假在线浮层（如 `OpenClawAskCopilotPanel`）与 7 个竞争抽屉，统一根据当前会话对象动态展示 Profile 详情、群成员管理、共享媒体/大纲、模型与工具绑定配置、会话关联子任务与 Routines。
6. **全局命令与模态层（Global Overlays & Modals）**：Universal Search（`Cmd/Ctrl+K`）、转发消息弹窗（`TdrpForwardMessageModal`）、音视频通话浮窗、Mini App 容器。

### 1.4 状态机一致性与隔离围栏（Fencing & Monotonic State Transitions）
1. **真实状态单调性**：状态转移必须保持单调推进（如：`Idle -> Pending -> Running -> (WaitingApproval | WaitingConnection) -> Terminal(Completed | Failed | Cancelled)`）。严禁使用前端 `setTimeout` 伪造回复、假装执行中或假装成功。
2. **多账号与设备安全围栏（Account Scope Generation Fencing）**：在切换账号（`accountScopeGeneration` 递增）或注销时，所有在途的异步任务、网络流、语音采集、草稿持久化及通知订阅必须原子熔断，迟到的旧账号事件必须被静默丢弃，绝不允许跨账号数据污染。
3. **会话级围栏（Session Key Fencing）**：在会话切换时，UI 视图、流式响应订阅、输入草稿和右侧 ContextInspector 必须严格绑定当前的 `session_key`，禁止并发或重连时的迟到数据写入错误会话。
4. **离线与断网显式表达**：未连接或认证中时，界面必须诚实展示“未连接 / 认证中 / 离线”状态，严禁为了界面好看而硬编码“全部连接器已就绪”或假在线红绿灯。

### 2.3 特殊职责解耦与路由指引

#### 1. `src/flows` 流程拆解规则
OpenClaw 上游的 `src/flows` 承担系统初始化、诊断自愈、渠道接入等业务流。在 Fabushi 统一架构中，绝不设立独立的“Flows 孤岛引擎”，而是依据具体行为严格解耦并注入既有领域：
- **配置与 Schema 初始化流（`src/flows/config-setup.ts`）**：归属于 **OCRM-M02**（蓝图 08），在 Host `settings_service.rs` 中原子应用；
- **渠道接入向导流（`src/flows/channel-setup.ts`）**：归属于 **OCRM-M14**（蓝图 07），收敛于右侧 `ContextInspector` 的渠道配置页；
- **Doctor 健康体检与修复流（`src/flows/doctor-health.ts`）**：归属于 **OCRM-M30**（蓝图 08），由 Host `host_diagnostics.rs` 权威驱动；
- **Provider 模型配置流（`src/flows/provider-flow.ts`）**：归属于 **OCRM-M06**（蓝图 03/04），接入统一输入台与设置面板。

#### 2. `src/transcripts` 媒体转录解耦规则
OpenClaw 的 `src/transcripts` 混合了实时语音采集、音频切片、会议记录与会话历史。在 Fabushi 中执行清晰的职责分离：
- **音频流物理采集与设备管理**：归属于 **OCRM-M25 / M26**（蓝图 06），由底层音视频引擎与平台适配器持有；
- **转写产物（Transcript Utterances）存储与消费**：仅归属于 **OCRM-M07**（蓝图 02），作为标准文本和结构化卡片载入唯一权威 `ConversationTranscript`；
- **媒体文件生命周期**：归属于 **OCRM-M23**（蓝图 06），通过统一附件协议管理缓存与下载。

### 3.3 原生网络与底层架构下沉说明（Native Messaging Architecture）

在将 Telegram Desktop 的 52 个能力域迁入 Fabushi 的过程中，遵循三条不可逾越的技术边界：
1. **彻底废除 MTProto 协议**：Telegram 官方的 MTProto 协议和 `tgcalls` 绝不作为 Fabushi 的运行时依赖。所有会话同步、消息投递、媒体传输均通过 Fabushi 原生网络服务（`Fabushi Native Network`）闭环承接：
   - 身份与认证：`source/electron-main/account/human-identity.ts`
   - 消息路由与状态落盘：`source/host/src/extensions/session/native_messaging.rs`
   - 媒体分发传输：`source/host/src/extensions/attachments/`
   - 实时信令交换：`docs/adr/FBCP-ADR-003-call-session-signaling.md`
2. **纯业务逻辑 Rust 沉淀**：Telegram Desktop 原 C++/Qt 源码中的数据模型（`data/`）、会话状态机（`history/`）、分片存储（`storage/`）全部以 Rust 重构并置入 `source/host/src/` 与 `native/mahayana-messaging/`，前端仅保留纯粹的 React/TypeScript 状态消费与渲染器。
3. **人机消息管道同构**：真人（Human）消息与 Agent 智能体生成内容共用统一底层管道，统一分配权威 `message_id`，统一支持编辑、撤回、表情表态与引用线程。

## 5. Fabushi Canonical State Owners 字典与反割裂规则

为了确保所有参与开发的子智能体（Worker Subagents）遵循统一的架构纪律，严禁出现“同一状态两处存、两个组件抢控制权”的现象，在此对核心状态权威归属进行强制限定：

### 5.1 核心 Canonical State Owners 字典

1. **会话与消息状态唯一权威（Conversation & Transcript Owner）**：
   - **前端**：`frontend/src/recovered/features/conversation/workspace/model.ts`
   - **后端存储**：`source/host/src/extensions/session/production.rs` 结合 `source/host/src/extensions/session/agent_db.rs`（SandAgentDb SQLite）
   - **铁律**：严禁在 `OpenClawAskCopilotPanel` 或其他组件中保存临时的本地聊天列表或消息数组。所有的发送、接收、更新、删除必须经由 `ProductionSessionWorkers` 并持久化至 SandAgentDb。
2. **输入台草稿与提交状态唯一权威（Composer & Draft Owner）**：
   - **前端**：`frontend/src/recovered/features/conversation/workspace/draft-state.ts` 与 `submission.ts`
   - **挂载点**：`frontend/src/recovered/features/conversation/workspace/composer.tsx`
   - **铁律**：整套界面只允许存在**唯一一个输入器**。切换会话或切换模式时，仅切换 `ConversationComposer` 的参数注入，禁止在右侧侧边栏或浮层中实例化第二个 `<textarea>` 或输入框。
3. **右侧上下文详情唯一权威（Context Inspector Drawer Owner）**：
   - **前端**：单一收拢的 `ContextInspector`（位于 `frontend/src/recovered/features/conversation/workspace/context-inspector/`）
   - **铁律**：彻底废除原独立的 7 个抽屉（`TdrpProfileDetailsDrawer`、`GroupMembersPane`、`ConversationOutlinePanel`、`AgentSettingsPanel`、`RoutinesInfoPane`、`ChannelsInfoPane`、`OpenClawAskCopilotPanel`）。根据当前的 `activeConversation` 类型和用户所选 Tab 动态切换渲染内容。
4. **任务与子代理状态机唯一权威（Tasks & Subagents Owner）**：
   - **前端**：`frontend/src/recovered/features/automations/async-tasks/provider.ts`
   - **后端**：`source/host/src/runner/subagent_runtime.rs` 与 `source/host/src/automations/`
   - **铁律**：任务状态完全由后台 Host 事件驱动。子代理的父子拓扑归属完全依据任务元数据中的 `parentId` 和 `taskId`，严禁通过字符串正则过滤代理名称。
5. **音视频呼叫会话唯一权威（Call Session Owner）**：
   - **契约**：`docs/adr/FBCP-ADR-003-call-session-signaling.md`
   - **实现**：`source/electron-main/media/` 与 `frontend/src/recovered/features/conversation/workspace/human-call-media.tsx`
   - **铁律**：通话状态直接挂载于对应会话上下文，支持最小化至顶栏指示条，严禁在全局脱离架构挂载孤立的通话全屏遮罩。

### 5.2 反割裂实施红线（Zero-Fragmentation Rules）
- **红线 1（代码行数预算）**：新建或重构的单一文件代码行数严格控制在 **200–600 行** 之间。超过 600 行必须依责任合理拆分子文件；低于 200 行的不必要薄胶水代码予以合并。
- **红线 2（命名空间规范）**：所有 UI 样式统一绑定 `--fabushi-*` 语义变量，禁止使用无收口的 `oc-*` 或未定义前缀，禁止在组件中直接写入硬编码十六进制颜色。
- **红线 3（单装配挂载入口）**：`frontend/src/production/ProductionRenderer.tsx` 保持单一顶层装配入口，所有新功能只能以窄接线（Narrow Wiring）契约通过 Props 传递，禁止在根部做复杂条件分叉。

## 6. 防作弊审计与独立验收标准（Anti-Cheating Oracle & Acceptance Checklist）

本规范设立严格的独立验收标准，由独立验收子智能体（Auditor / Challenger）对照以下检查表逐项核验。任何一条违反均视为作弊，直接判决交付不合格：

### 6.1 负例作弊排查表（Forbidden Patterns Checklist）

- [ ] **严禁本地 `setTimeout` 假逻辑**：代码中严禁出现使用 `setTimeout` 伪造 LLM 回复、伪造工具执行成功或伪造网络连接的逻辑（如原 `OpenClawAskCopilotPanel.tsx` 中的模拟回复）。
- [ ] **严禁硬编码虚假在线状态**：严禁硬编码 `isGatewayOnline={true}`、`"18 个连接器全量就绪"` 或永远为绿色的网络指示灯。未连接时必须明确展示“离线/未连接”。
- [ ] **严禁并行的第二输入器**：界面中除了主 `ConversationComposer` 之外，严禁存在第二个能够发送消息的输入框。
- [ ] **严禁硬编码模型列表**：`AVAILABLE_MODELS` 数组必须由 Host 动态配置下发，当无可用模型或未连通时必须正确展示禁用或指引状态，严禁在前端写死静态 mock 列表。
- [ ] **严禁按名称过滤子代理**：严禁出现类似 `agent.name.includes("executor")` 的粗暴字符串过滤逻辑，必须且仅能依据元数据 `parentId` / `taskId` 归拢子代理。
- [ ] **严禁覆盖用户未发送草稿**：在快捷发送投票、待办或发票时，严禁清空或覆盖用户正在主输入框中编辑的未提交文本草稿。
- [ ] **严禁凭空伪造文件路径或 API**：所有在蓝图与实现中引用的文件路径、Rust Struct 与 TypeScript 接口必须在代码库中物理存在且可引用，严禁凭空捏造。
